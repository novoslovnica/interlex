## Notes for Claude sessions on this repo
- **Production is the source of truth for interlex.db/auth.db/library.db since 2026-09-24** — never plan to "fix it locally and upload the file". Data changes go through `scripts/db/manifest.ts` + `bash prod.sh run <script>` (dry run, then `--apply`); see AGENTS.md "Production data changes". Start from `bash scripts/local/pull-prod.sh`, not from whatever local copy is lying around.
- **All four live SQLite databases with real data are plain files in the project root**, not under `prisma/`: `interlex.db`, `auth.db`, `library.db`, `corpus.db` (confirmed via `.env`'s `DATA_DATABASE_URL`/`AUTH_DATABASE_URL`/etc. and `.env.development`'s `SQLITE_DB`). `prisma/*.schema.prisma` are schema *source* files only — the actual `.db` files they point at live at the repo root, not inside `prisma/`. Before writing any DB-touching script or migration, `cat .env` to confirm the current path rather than assuming. Treat these files with the same care as production data — back up before any raw-SQL DDL/migration.
- Incident chronicle (July–September 2026) lives in `docs/history/` — check it for the "why" behind a rule before re-litigating it; AGENTS.md itself only carries the standing rules.
- [ARCHITECTURE.md](ARCHITECTURE.md) has an up-to-date system diagram plus a "Known Issues & Technical Debt" section — check it before assuming something is broken or missing; several items (word frequency/CEFR, corpus DB, four-database split) are already shipped despite older docs/instincts suggesting otherwise.
- Any code touching semantic relations (synonym/antonym/hypernym/.../derivation) must go through `lib/relations.ts` (`fetchSymmetricSemanticRelations`/`saveSymmetricSemanticRelation` and the directional helpers), not a fresh `WHERE sourceId = ?` query against `semantic_relations` — that pattern is exactly what caused the original bidirectionality bug.
- When adding any API route under `app/api/**` that mutates lexical/relation data, always gate it with `checkPermission(session, Feature.X)` for the specific action (see `lib/permissions.ts`, `config/features.ts`) — a session check alone is not enough, and this exact gap is what caused the word-relations vulnerability.
- **`prisma migrate dev` is currently unsafe on the `data` schema** — it detects drift (`morpheme_allophones`, `proto_slavic_words` changed outside any migration) and offers to reset the DB, which would delete all lexical data. Don't run it until this is reconciled. Schema-only changes (no new Prisma-modeled fields) are applied as raw idempotent SQL scripts through the `scripts/db/manifest.ts` `schema` kind instead.
- **The system `sqlite3` CLI on a host and the SQLite bundled inside `better-sqlite3` (what the app actually runs on) can be different builds with different capabilities.** Learned this the hard way: production's `sqlite3` CLI lacked the FTS5 trigram tokenizer and failed mid-migration, dropping `lexemes_text`/`lexeme_allophones_text` without being able to recreate them. For any DB DDL that depends on an optional SQLite feature (FTS5 tokenizers, JSON1, etc.), prefer a Node script using the project's own `better-sqlite3` (`npx tsx scripts/db/....ts` — probe for the feature in a throwaway `temp` table before touching real tables) over a raw `.sql` file run through the host's system CLI.
