# Выкладка работ по распознаванию корпуса (2026-08-24/25)

Заметка на один конкретный деплой, где `corpus.db` переносится с локальной
машины, а `interlex.db` на проде **остаётся своя** — она там обрастает новыми
переводами, и заменять её нельзя.

## Что где лежит

Работа затронула две базы, и переносится только одна из них.

**`corpus.db` — переносится целиком.** Здесь вся переразметка: `CorpusToken`
(5,1 млн), `CorpusTokenCandidate`, `CorpusCandidateProposal` вместе со
статусами и решениями модератора.

**`interlex.db` — НЕ переносится, изменения нужно воспроизвести скриптами.**
Здесь оказалось шесть правок, без которых прод разойдётся с переносимым
корпусом:

| что | чем воспроизвести |
|---|---|
| форма `je` привязана к `byti` | `scripts/db/2026-08-24-add-je-inflection-anomaly.ts` |
| 16 дублей в `inflection_anomalies` | `scripts/db/2026-08-24-dedupe-inflection-anomalies.ts --apply` |
| стем `ne-ADV`, `isPublic=0` у 3 097 пустых лексем | `scripts/db/2026-08-24-fix-dictionary-defects.ts --apply` |
| 9 окончаний класса `verb_present_athematic_a` | `scripts/db/2026-08-24-add-athematic-a-present-endings.ts --apply` |
| частотность и уровни CEFR | `npm run compute:frequency` |
| дубликаты в `candidates` | `scripts/db/2026-08-25-dedupe-corpus-candidates.ts --apply` |

Все скрипты идемпотентны и отбирают строки **по условию, а не по id**
(по слугу, по типу основы, по «нет ни одного значения»), поэтому расхождение
прод-словаря с локальным им не мешает: если на проде кому-то из тех 3 097
лексем уже добавили значение, скрипт её просто не тронет.

## Порядок

1. Скрипты 1–4 из таблицы выше — **до** подмены корпуса. Они меняют то, как
   движок порождает и распознаёт формы; без них прод-анализатор будет вести
   себя иначе, чем тот, что произвёл переносимые данные, и следующий же
   реанализ на проде откатит часть улучшений.
2. Подмена `corpus.db`.
3. **Перезапуск процесса приложения** — не просто деплой файлов. Долгоживущий
   `next start` держит в памяти ранее загруженный Prisma-клиент и индексы
   анализатора (`createDbAnalyzer` строит их лениво и кэширует на процесс).
4. `npm run compute:frequency` — **после** подмены корпуса: он читает
   `corpus.db` и пересчитывает частотность и CEFR по лексемам прод-словаря.

## Одна известная неточность, не влияющая на работу

`CorpusCandidateProposal.candidateId` ссылается на `Candidate.id` из
`interlex.db` — это обычный `Int` без внешнего ключа, базы никогда не
джойнятся. После переноса корпуса эти ссылки на проде будут указывать в
пустоту (или, если в прод-таблице `candidates` уже что-то есть, — на чужие
строки, у неё свой автоинкремент).

Функционально это ничего не ломает: колонка только пишется, ни один запрос
её не читает — она нужна как след происхождения. Значимо только то, что сами
записи `Candidate`, созданные одобрениями в очереди, живут в `interlex.db` и
на прод не поедут. На момент этой заметки их две (`medžuslovjansky`, `tuty`) —
дешевле повторить эти одобрения на проде, чем переносить строки.

**Дальше это будет копиться.** Каждое одобрение в `/admin/corpus-candidates`
пишет статус в `corpus.db`, а саму запись — в `interlex.db`. Если разбирать
очередь локально, а словарь вести на проде, они будут расходиться. Разумнее
разбирать очередь там же, где живёт словарь, то есть на проде.
