# Выкладка и откат

`bash release.sh` собирает отдельный релиз, не меняя `.next` и зависимости
работающего приложения. Перед запуском нужны commit + push: локальный HEAD должен
совпадать с `origin/main`. Сервер собирает именно этот SHA, даже если main успел
продвинуться во время загрузки.

## Каталоги на сервере

Корень `/var/www/interslavic-lexicon.com/interlex` остаётся управляющим checkout и
постоянным хранилищем пяти SQLite-баз, серверных `.env*`, `public/covers`,
`public/audio`, `exports` и `logs`. Базы не копируются в каталоги приложения:
`release-env.sh` задаёт абсолютные пути для Prisma, raw SQLite и DB runner.
Загруженные файлы, выгрузки Hunspell и журнал DB runner также используют общие пути.
Настроенные в серверных dotenv COVERS_DIR/AUDIO_DIR/HUNSPELL_OUT_DIR сохраняются;
для собственных путей используйте абсолютные значения.
`prod.sh` запускает скрипты из **активного** релиза, а `pull-prod.sh` и offsite backup
продолжают читать базы по прежним путям.

- `.releases/<time>-<sha>-<pid>` — отдельный git worktree с собственными
  `node_modules`, Prisma-клиентами и `.next`.
- `current` — симлинк активного релиза; `previous` — предыдущего успешного.
- `.deploy/<id>` — снимки, экспорт ручных правок корпуса, резервные копии затронутых
  баз в `rollback/`, итоговый `result` (0 — успех, другое число — ошибка).
- `logs/releases/<id>.log` — полный журнал, включая результат восстановления.

Серверные env-файлы подключаются симлинками. `release.sh` **не загружает секреты**
с локального компьютера. Изменение конфигурации выполняется отдельно на сервере.

## Порядок релиза

1. Загрузка файлов в уникальный staging-каталог. Для корпуса — прежний протокол
   экспорта/импорта ручных правок модераторов.
2. Локальный lock защищает подготовку снимков от второго запуска. Фоновый
   supervisor и `flock`: одновременно выполняется только один релиз.
   Обрыв SSH не прерывает сборку или восстановление. Даже ранний отказ (занятый
   lock, ошибка настройки) записывается в `result`.
3. Чистый worktree фиксированного коммита: `npm ci`, пять Prisma generate,
   `npm run build`, проверка `BUILD_ID` и целостности загруженных снимков.
   Служба продолжает обслуживать запросы. В next.config явно закреплён корень
   worktree, чтобы Next не выбирал внешний checkout по его package-lock. Нужны Linux, `flock`, GNU coreutils,
   sqlite3, curl и Node из nvm; существующие sudo-права systemctl/chown/journalctl.
4. Захват `.db-run.lock` на весь критический участок; DB runner наследует его.
   План миграций читается без создания реестров, проверяет checksum и запрещает
   незаявленную совместимость с прежним кодом. Проверяется место под резервные копии.
5. Остановка службы, повторная проверка fingerprint ручных правок корпуса,
   SQLite `.backup` затронутых баз, замена явно выбранных снимков, схемные миграции.
   Data-скрипты автоматически не запускаются.
6. Обновление управляющего checkout (без сборки/установки зависимостей),
   атомарный `rename` нового симлинка поверх `current`, запуск службы.
7. Проверка systemd и HTTP `/api/health`: endpoint читает все пять баз, отдаёт
   `Cache-Control: no-store`, успешный статус и SHA **запущенного** релиза.
   Чужой/старый процесс не проходит проверку. Затем проверяются публичный endpoint,
   главная страница и по одному JS/CSS-ресурсу: ошибка reverse proxy или устаревший
   alias статики также запускает откат. Только затем обновляется `previous`.
   По умолчанию публичный адрес — https://www.interslavic-lexicon.com;
   `INTERLEX_PUBLIC_URL` меняет его (пустое значение отключает внешнюю проверку
   исключительно для изолированного тестового окружения).

Первый релиз сохраняет прежний checkout в legacy-worktree, подключая старые
`.next`, `node_modules`, Prisma-клиенты и общие файлы. Существующий systemd
(`npm run start --prefix <root> -- -p 3010`, WorkingDirectory=root) менять не нужно:
новый npm start запускает `scripts/ops/start-release.sh`, выбирающий `current`.
До установки launcher обычный `npm start` по-прежнему работает локально.

## Что происходит при ошибке

Ошибка установки/сборки оставляет работающую службу и её файлы нетронутыми.
После остановки любой сбой запускает восстановление и проверку прежней версии.

**До попытки запуска кандидата** восстанавливаются изменённые базы из снимков и
прежний симлинк. После попытки запуска откатывается **только код**: новая версия
могла уже принять правки, и автоматическое восстановление базы затёрло бы их.
Поэтому все новые schema-миграции должны явно задавать `rollbackSafe: true` в
`manifest.ts` и сохранять чтение/запись предыдущей версии (expand/contract).
Это декларация автора, а не автоматическое доказательство совместимости.
Удаление/переименование используемых полей требует отдельного плана перехода.
Применённые migration-файлы не редактируют — checksum drift останавливает релиз.

`--skip-backup` больше не поддерживается: он несовместим с восстановлением после
частично выполненной миграции/замены. Реестр дополнительно сохраняет собственные
резервные копии перед схемными миграциями. На время критического участка внешние
писатели, обходящие DB runner, должны быть остановлены. SIGTERM/INT запускает
восстановление; SIGKILL/перезагрузка машины требуют проверки вручную.

## Ручной откат и диагностика

```bash
bash release.sh --rollback
```

Команда переключает `current` и `previous`, перезапускает службу и проверяет
готовность. Базы и миграции не откатываются, изменения пользователей сохраняются.
Параметры загрузки данных с `--rollback` несовместимы. Откат использует тот же
фоновый supervisor и блокировки; если целевая версия не запускается, возвращается
версия, активная до команды. Повторная команда позволяет вернуться обратно.

При потере SSH не запускайте второй релиз вслепую: release.sh печатает точные пути
лога и `result`. Отсутствие результата означает, что выполнение ещё идёт либо
процесс был принудительно убит. В журнале успешного восстановления есть
`ROLLBACK OK`; `CRITICAL` означает, что нужна ручная проверка службы/данных.
Перед удалением оставшегося `.db-run.lock` проверьте записанный PID и фоновые задачи.

Релизы и DB-снимки намеренно не удаляются автоматически. Контролируйте место на
диске; удаляйте ненужные worktree через `git worktree remove --force <path>` только
после проверки `readlink -f current` и `readlink -f previous`. Legacy-worktree и
корневые `.next`/`node_modules` нужны, пока legacy может служить откатом. Журналы и
резервные копии из `.deploy/*/rollback` удаляйте отдельно по принятому сроку хранения.
Сборка отказывается стартовать при свободном месте меньше 2 GiB; перед остановкой
проверяется дополнительный запас на копии затронутых баз.

Основные шрифты Geist, Geist Mono и Noto Sans хранятся в `app/fonts/` и подключены
через `next/font/local`. Чистая сборка не обращается за ними к Google Fonts:
его extensionless font URLs ломали Next 16/Turbopack на первом изолированном
релизе (https://github.com/vercel/next.js/issues/99114). Лицензии и исходники —
`app/fonts/README.md`. Декоративные Monomakh/Glagolitic загружаются браузером
отдельно и не участвуют в сборке.
