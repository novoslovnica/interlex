# Production ↔ local divergence and the 2026-09-23 reconciliation

> Вынесено из AGENTS.md при реструктуризации 2026-09-26.

The production `interlex.db` and the local one had been diverging since about 2026-07-20 (last upload): moderators worked on production (mk/hr translation cards, CORE-form checks, two merges, candidates), while every September script (merges, capitalization, voda split, community tables) ran locally only. Before the local snapshot could replace the production file, the production work was pulled in with `scripts/db/2026-09-23-import-prod-moderation.ts <export-dir> [--apply]` (idempotent; the export is produced on the server by read-only better-sqlite3 scripts run with `NODE_PATH=$PWD/node_modules` — production's `sqlite3` CLI is too old for `-json`).

What the comparison established — check these before trusting any id across the two databases:
- **meaning ids match** (verified by text); **translation ids, candidate ids and root_discovery_proposals ids do not** (tables rebuilt at different times) → translations key by `(meaningId, language)` + case-insensitive value, candidates are replaced wholesale, root decisions match by `(clusterKey, method)`; `lexeme_allophones` ids match for most rows but not all → key by `(lexemeId, flavor, type)`.
- The local 2026-07-23/24 translation consolidation **lost ~7 300 rows of the July import** that production still has (`abhazsky` had 17 languages on production and none locally). 6 277 of them were gap-filled (local had no row in that language); 1 013 where local holds a different value were written to `prod-translation-disagreements.json` (gitignored) for the maintainer — a mix of synonyms («Лысый»/«безволосый»), variant duplicates («Theater» vs «theatre, theater») and **local misattachments** («Информация» vs local «данник, платящий дань»; `blud` = «Блуд», not «ошибка»). Not decided yet.
- Case-only differences are resolved toward the lowercase form (the local capitalization pass), never toward production's import capitals; a local `verified=1` is never cleared by a production 0/NULL.
- Production's `sqlite3` is old; `USERNAME` is a special read-only variable in zsh, so `.env.release`'s login must be read into another variable (release.sh only works because it runs under bash).
- Still on production only after the upload: nothing — but `2052 no-pron` (deleted locally without a merge record) and `25508 značenje-NOUN` (promoted on production, probable duplicate of 22199) deserve a look in `/admin/deduplication`. `corpus.db` was not part of this reconciliation: production's copy still carries pre-merge slugs.
