# Bots: shared core — 2026-09-24 (phase 2 of direction 6 of docs/strategy-directions-2026-09-19.md)

> Вынесено из AGENTS.md при реструктуризации 2026-09-26.

Telegram and Discord bots (phases 3–4, not built yet) run inside the Next process as webhook routes and call `lib/` directly — the public API returns neither paradigms nor transliteration, and one shared key would give every bot user the same 60/min limit. The shared core is platform-neutral:

- `lib/paradigm.ts` — **the single source of paradigms** for the word page and the bots: `buildNounParadigm`, `buildVerbParadigm`, `buildAdjectiveColumns`, plus `toParadigmSource(item)` (a `lexemes` row → input). `app/words/[id]/page.tsx` (nouns), `Word.tsx` (verbs) and `AdjectiveDeclensionTables.tsx` now call it instead of the engine directly. Pure module (no DB, no next/*), safe on the client. A new paradigm-showing surface must go through it too — two copies of noun declension already drifted once (see `2026-07-25-noun-declension-consolidation.md`). (Standing rule, repeated in AGENTS.md.)
- `lib/orthography/standard.ts` — moved from `lib/export/hunspell/orthography.ts`; also `latinToCyrillic` / `cyrillicToLatin` / `isCyrillicText` for text (standard Cyrillic with ј/љ/њ/є; ѣ and ѧ/ѫ are read on input). (Standing rule, repeated in AGENTS.md: standard orthography conversions go through this module.)
- `lib/bots/core/lookup.ts` — `lookupWord(query, languages)`: Cyrillic → Latin; inflected form → lemma through the corpus `DbAnalyzer` (`lib/bots/core/analyzer.ts`, a lazy per-process singleton — the first request starts a ~20 s build and is answered from the dictionary alone until it is ready); otherwise an in-memory index of all public lexeme spellings without diacritics (exact match, then prefix / Levenshtein ≤ ⅓ of the length; refreshed every 10 min). The site's FTS5 trigram index is not used: it only finds substrings with the exact diacritics ("človek" never finds "člověk"). Display spelling is `canonicalFromStem(value, stem)` (value is often undiacriticized). `splitMeaning` parses `meanings.meaning` (stored as "definition;lemma.;*example*" in varying order).
- `lib/bots/core/wordOfDay.ts` — deterministic per UTC day (SHA-256 of the date) over public NOUN/VERB/ADJ/ADV lexemes of CEFR A1–B2 with a verified en/ru translation (~5.9k). Use `l.id IN (subquery)`, not `EXISTS` per lexeme: 0.5 s vs ~50 s on the live DB.
- `lib/bots/core/{commands,compose,message,labels}.ts` — `runCommand(BotCommand, {languageCode})` → `BotMessage` → `toTelegramHtml` / `toDiscordEmbed`. Commands: lookup, forms, cyr, lat, today, help. Bot UI texts ru/en/isv in `labels.ts` (no request locale in a webhook, so not next-intl).

**Fixed on the way** — adjective tables on the word page showed the bare stem in every cell ("dobr") for every adjective: `getEnding` (`lib/grammar/endingLoader.ts`) returns `''` when the ending is missing, so `generateAdjectiveForm`'s `?? ADJECTIVE_ENDINGS_REGISTRY[...]` never fell back — and in the browser, where there is no DB, every ending was missing. Added `findEnding` (returns `undefined`) and used it in `lib/grammar/adjective/index.ts`. The server side (corpus engine, bots) was never affected: there the DB has the endings.

## Addendum 2026-09-26: Telegram webhook (phase 3)

The Telegram bot over the shared core (roadmap item 53) ships as a webhook route, no separate process:

- `app/api/bots/telegram/route.ts` — POST webhook. Verifies the `x-telegram-bot-api-secret-token` header against `TELEGRAM_WEBHOOK_SECRET` with `crypto.timingSafeEqual` (length check first, same pattern as `auth.config.ts`). If the env var is unset the request passes with a one-time `console.warn` — convenient in dev, **must be set in production**. Parses the update via `lib/bots/telegram/update.ts`, runs `runCommand(cmd, {languageCode, botName: TELEGRAM_BOT_NAME})`, answers with Telegram's "reply directly from the webhook" convention: `NextResponse.json({method: "sendMessage", chat_id, text, parse_mode: "HTML"})` (text from `toTelegramHtml`). Non-text updates and unparseable bodies get an empty `200 {}` — Telegram retries anything that isn't 2xx. Errors inside `runCommand` return a polite message to the user and `console.error` server-side.
- `lib/bots/telegram/update.ts` — pure `telegramUpdateToCommand(update)`: `/start`, `/help` → help; `/forms`, `/cyr`, `/lat` with argument; `@botname` suffix stripped; empty argument → help (usage hint is in the help text); `/today`; plain text → lookup; bot messages and non-text updates → null. Minimal local `TelegramUpdate` type, no `any`.
- `proxy.ts` — `/api/bots/*` bypasses the 120/min IP limiter (same exemption as `/api/auth`): all updates arrive from Telegram's server IP ranges, so a shared per-IP bucket would drop updates as soon as several chats use the bot. Forgery protection is the secret-token check in the route instead.
- `scripts/ops/telegram-set-webhook.ts` — `npx tsx scripts/ops/telegram-set-webhook.ts [--drop]`: getMe → setWebhook(`${NEXTAUTH_URL or SITE_URL}/api/bots/telegram`, `secret_token`, `allowed_updates: ["message"]`, `drop_pending_updates` only with `--drop`) → getWebhookInfo. Idempotent. Env: `TELEGRAM_BOT_TOKEN`, `NEXTAUTH_URL`/`SITE_URL`, `TELEGRAM_WEBHOOK_SECRET` (all required); `TELEGRAM_BOT_NAME` (optional, shown in the help text as `@bot`).

Discord bot remains phase 4, same core.

## Addendum 2026-09-27: long-polling fallback + shared update handler

Telegram reported `Connection timed out` on the production webhook — the host is reachable from the public internet, so the inbound IP ranges of Telegram (149.154.160.0/20, 91.108.4.0/22, …) are almost certainly blocked by the server's firewall or, more likely, the hosting provider. Two changes:

- `lib/bots/telegram/handle.ts` — the per-update logic (`telegramUpdateToCommand` → `runCommand` → `toTelegramHtml`, plus the polite-error catch) extracted from the webhook route into `handleTelegramUpdate(update): Promise<{chatId, html} | null>`. The route and the poller share it; they differ only in delivery (direct webhook reply vs an explicit `sendMessage` call). 3 unit tests (`handle.test.ts`, mocked `runCommand`).
- `scripts/ops/telegram-poll.ts` — long-polling loop (`getUpdates`, `timeout: 50`, `allowed_updates: ["message"]`): `npx tsx scripts/ops/telegram-poll.ts` runs forever (run it under systemd/supervisor/tmux — it does not daemonize itself), `--once` processes a single batch, `--takeover` calls `deleteWebhook` first (a set webhook and `getUpdates` conflict with 409 — on startup the poller refuses to run while a webhook is active, unless `--takeover`). The offset is persisted to `logs/telegram-poll-offset.txt` (gitignored) so a restart does not reprocess old updates. 409 from Telegram (another poller/webhook instance) stops the loop with a clear message; other API/network errors retry after 5 s. Env: same `TELEGRAM_BOT_TOKEN` (+ `TELEGRAM_BOT_NAME`); loads `.env.production`/`.env` via dotenv like `telegram-set-webhook.ts`.

The webhook mode stays the default — it needs no long-lived process. Switch to polling only if the provider block is confirmed unfixable.

## Addendum 2026-09-30: standalone service architecture (polling dropped)

Supersedes the webhook-route design above (phase 3 addendum) and the polling fallback (2026-09-27 addendum — deleted without ever running in production beyond its startup guard): Telegram could not reach the main server at all (`Connection timed out` — host publicly reachable from elsewhere, so inbound Telegram IP ranges are blocked at provider/firewall level). Maintainer decision: **the bot is a separate service on a separate server** — one that Telegram can actually reach; the main site stays where it is and knows nothing about the bot.

- `services/telegram-bot/server.ts` — standalone Node HTTP service (no Next): POST accepts a Telegram update on any path (verified against `TELEGRAM_WEBHOOK_SECRET` via `timingSafeEqual`), answers with the direct-reply convention (`{method: "sendMessage", ...}`), so the service never calls the Bot API and needs no token. `GET /healthz` → `{ok, analyzerReady}`. Form analyzer warms at startup (~20–30 s). Env: `TELEGRAM_WEBHOOK_SECRET` (refuses to start without), `DATA_DATABASE_URL` + `SQLITE_DB` (a **snapshot copy** of `interlex.db` — the service never opens a connection to the production server), `BOT_PORT`. Full deploy guide: `services/telegram-bot/README.md` (bundle → scp → `npm i --omit=dev` → systemd → nginx+TLS → nightly DB snapshot sync → `telegram-set-webhook.ts --origin https://<bot-host>`).
- `scripts/ops/bundle-telegram-bot.ts` (`npm run bot:bundle`) — esbuild bundle (`format: "esm"`, `createRequire` banner for bundled CJS deps like dotenv). Only project code is bundled; `better-sqlite3`, `@prisma/client`, `@prisma/adapter-better-sqlite3` stay external (native module must build for the target machine) and are pinned into `dist/package.json` from the root manifest. Verified end-to-end from a bare directory with just `dist/` + `npm i --omit=dev` + a copied `interlex.db`: lookup, inflected-form→lemma through the warmed analyzer, locale detection (ru/en), 403 on bad secret.
- Removed: `app/api/bots/telegram/route.ts` and the `/api/bots` exemption in `proxy.ts` (single delivery path — the service), `scripts/ops/telegram-poll.ts`. Shared per-update logic stays in `lib/bots/telegram/handle.ts` (used by the service, covered by unit tests).
- `scripts/ops/telegram-set-webhook.ts` — webhook origin is now the **bot service host**: `--origin <url>` flag or `BOT_ORIGIN` env, falling back to `NEXTAUTH_URL`/`SITE_URL`; URL path changed from `/api/bots/telegram` to `/` (single-purpose service).

## Addendum 2026-10-04: inline mode, etymological display, dual number (user feedback)

First live feedback round after the bot went to production (@InterlexAuthBot). Three fixes, all in the shared core, deployed to server 2 same day:

- **Inline mode** (`@InterlexAuthBot слово` in any chat) — promised in the help text since the core was built, never wired up. `telegramUpdateToInlineQuery` (update.ts) → `handleTelegramUpdate` now dispatches to `buildInlineResults` (handle.ts): empty query → word of the day; otherwise up to 5 `entryMessage` cards as `InlineQueryResultArticle`s (title, description = subtitle + first line, message text via `toTelegramHtml`, URL button from `msg.link`). Answered via the direct-reply convention as `answerInlineQuery` (`cache_time: 300, is_personal: true` — content is locale-dependent). Results cached in-process (5 min TTL, 500 entries, `lib/bots/telegram/inline.ts`) — inline fires a request per keystroke. `allowed_updates` in `telegram-set-webhook.ts` extended to `["message", "inline_query"]`; webhook re-registered.
- **Etymological (classical) display** — `compose.display()` was converting every form to standard simplified spelling via `toStandardLatin` (bot predated the maintainer's 2026-09-26 canonical decision). Now it only strips stress marks and keeps etymological letters (`język`, `vodų`, `stolěťa`); Cyrillic stays standard (є), as on the site. `stripStress` exported from `lib/orthography/standard.ts`. Also `/forms` title: the raw `lexemes.value` is often undiacriticized ("jezyk"), so the paradigm source now takes the canonical value from the lookup entry (`canonicalFromStem` already applied there) — title and table no longer disagree.
- **Dual number** — `buildNounParadigm` computed dual all along; the bot table rendered only sg/pl. Now `[sg, du, pl]` columns with the `dual` label (дв./du/dv.) in all three locales.

Verified live on server 2: `/forms język` → title `język`, table with dual column (`języka / języku / językoma`); inline query → correct `answerInlineQuery` payload. Tests: +13 (update parsing, inline results/caching/error path, display spelling, dual column). 391 green, gates at baseline.

Inline follow-up (same day): user reported "@bot voda shows nothing" while DM mode worked. Server-side forensics: nginx access log has **no vhost column** (default format — the domain only appears in Referer of browser hits), Telegram webhook POSTs come from 91.108.0.0/22 / 149.154.160.0/20 with empty User-Agent — filter by those. `getWebhookInfo` was completely clean (no `last_error_message`, `allowed_updates: ["message","inline_query"]`), Telegram-range POSTs got 200s. Conclusion: with inline mode disabled in BotFather, clients never generate `inline_query` at all — nothing reaches the webhook and there is no error anywhere; it can only be enabled via @BotFather (Bot Settings → Inline Mode). Documented in services/telegram-bot/README.md.

## Addendum 2026-10-06: inline answers need a direct Bot API call (webhook reply silently ignored)

The 2026-10-04 conclusion above ("inline mode disabled in BotFather") was **wrong**. Re-checked live: `getMe` → `supports_inline_queries: true`, and `inline_query` updates **did** reach the service (confirmed with a temporary per-update log in the deployed bundle + nginx: POSTs from 91.108.5.42 carrying `inline_query` payloads, `query: "voda"`). The real cause: answering the inline query with the **direct-reply convention** (`{method:"answerInlineQuery", inline_query_id, results, ...}` as the webhook response body) makes Telegram silently drop it — nothing appears in the client, no error anywhere (`getWebhookInfo` stays clean, the service already answered 200; the webhook-reply path can't report method errors). The *same* payload sent as a normal POST to `https://api.telegram.org/bot<token>/answerInlineQuery` works (`ok:true`, cards appear). So despite Telegraf's webhook-reply allowlist including `answerInlineQuery`, in practice it isn't executed for inline queries.

Consequences:
- `services/telegram-bot/server.ts` now needs `TELEGRAM_BOT_TOKEN` and **refuses to start without it** (abandoning the "token not needed" design for inline); inline is delivered by `deliverInline` (explicit `answerInlineQuery`), errors logged to stderr. `sendMessage` still uses the direct-reply convention (one fewer request, proven to work).
- Inline mode also gained command support: a query starting with `/` runs the core command (`/today`, `/forms`, `/cyr`, `/lat`, `/help`) and returns one card — previously every query (including `/today`) was treated as a word, so commands came back empty. `lib/bots/telegram/handle.ts::buildInlineResults` + tests.
- Diagnostic method that settled it: temporary `appendFileSync` of `{keys, inline_query.query, message.text}` in the deployed `server.mjs`, then read the log after live tests. Reverted; the deployed file is now a normal `npm run bot:bundle` build.
