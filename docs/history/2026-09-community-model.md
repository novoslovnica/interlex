> Вынесено из AGENTS.md при реструктуризации 2026-09-26. Действующие правила этой области собраны кратко в AGENTS.md, секция "Standing Rules".

Built: phases 0–3 (user languages, opt-in public handle, role audit; public translation review cards; moderator queue, control cards, reputation; public profile, leaderboard, completeness dashboard, moderator-role proposals). Phases 4 (public word history) and 5 (word discussions) built 2026-09-23 — every phase of the plan is now in place; phase 6 (launch, further micro-task types) is operational, not code.

**Rules that hold for everything in this direction:**
- A participant's name reaches public output only through `lib/community/identity.ts::resolvePublicNames` (handle from `UserProfile`, or nothing → "Anonymous"). Never read `User.name`/`User.email` or `AuditLog.userEmail` for public pages — a Telegram user's email is `<username>@telegram.user`.
- Self-service actions are session-only, no `Feature` (same as `FlashcardProgress`/`ApiKey`); a `Feature` is added only for a moderator-facing view.
- Volunteer consensus **never writes `Translation.verified`** — that stays the moderator's mark. Consensus lives in `translations.communityStatus` (`confirmed|rejected|disputed`, null while collecting) + `communityYes/communityNo` (sums of vote weights, recomputed from `translation_votes` on every vote, never incremented).
- Card pool = `verified IS NOT 1` (the maintainer chose to trust the existing `verified=1`, although most of it is a bulk-import flag: `audit_logs` had zero `${lang}.verified` rows when this was built), non-empty value, `communityStatus IS NULL`, public lexeme with a POS, no active vote by this user. Started cards first, then by `corpusFrequencyPerMln`, random within the top 200.
- Thresholds live in `lib/community/consensus.ts` only: margin of 3 → confirmed/rejected, 7 decisive answers without a margin → disputed; "unknown" never counts.
- `upsertTranslation` calls `resetCommunityReview` when the **value** changes (votes → `stale=1`, tally cleared); a `verified`-only change leaves votes alone, they are needed later to score participants. "One active vote per (translation, user)" is a **partial** unique index (`WHERE stale = 0`) created by the raw-SQL migration — Prisma cannot express it, so `TranslationVote` has no `@@unique`; do not "fix" that by adding one, it would block re-voting after a value change.
- Per-user limits (30/min in memory, 500/day counted from `translation_votes`) are enforced in the route, not in `proxy.ts` — the proxy runs on Edge without DB access and only knows the IP.
- Client components must import shared constants from `lib/community/constants.ts`, not from `translationCards.ts` (it pulls `crypto`/better-sqlite3 types) — `import type` from it is fine.
- A consensus outcome is written to `audit_logs` as `userEmail='community'`, `userId=NULL`, field `${lang}.communityStatus`, by a synchronous raw INSERT inside the vote transaction.
- `/words/[id]` resolves by **numeric lexeme id**, not slug (`getItem` does `WHERE id = ?`) — link to `/words/${lexemeId}`.

## Phase 2: judging answers, control cards, moderator queue

- **`translation_votes.agreed` is the source of truth for reputation** (1/0 once judged, NULL before); `contributor_stats` is only its aggregate, kept current by `refreshContributorStats` and rebuildable with `scripts/db/recompute-contributor-stats.ts`. It is stored on the vote rather than derived on read because a moderator replacing a wrong value marks the votes `stale`, and "these people were right" has to survive that.
- **`settleVotes(db, translationId, outcome)` must run BEFORE anything that changes the value** — it only touches `stale = 0` votes, and `upsertTranslation` marks them stale on a value change. `resolveReview` does this in the right order; any new code path that replaces a community-reviewed value must too.
- Who settles: consensus (`confirmed`→yes, `rejected`→no; provisional), a moderator's explicit decision in the queue, and `upsertTranslation` when `verified` becomes 1 with the value unchanged. A later call overwrites an earlier one — the moderator outranks the consensus. A plain value edit elsewhere deliberately settles nothing: it may be a typo/case fix, not a verdict on the old value. `disputed` and `unknown` are never judged.
- **Weight** (`lib/community/reputation.ts`, pure): 1 until 20 judged answers (votes + controls), then 0.25 / 1 / 1.5 / 2 by accuracy; failing the controls (<50% on 10+) gives weight 0 + `flagged`. Only failed controls zero a participant — low agreement alone can be honest disagreement with the majority. The weight is snapshotted onto the vote when it is cast; zero-weight votes do not count toward the 7-answer `disputed` limit either.
- **Control cards** (`controlCards.ts`): a `verified=1` translation shown as is (`control_yes`) or with the value of another same-POS word's translation (`control_no`, built on the fly, never stored). 25% of cards until a participant has 10 control answers, then 10%. Languages with no `verified=1` translation (hsb, dsb, mk today) get none. Known imprecision: a random decoy can occasionally be a valid synonym — hence the soft flag threshold.
- **The client must not be able to tell a control card from a regular one.** Every card carries an HMAC token (`cardToken.ts`, keyed by `AUTH_SECRET`, bound to user + translation); the kind is not encoded in it — the server recovers it by trying the three kinds. The vote response for a control card is identical to a regular undecided one. Do not add a field to the card or the response that differs by kind.
- **Moderator queue** `/admin/community-review`: `Feature.CommunityReview` to view, plus `translate_<lang>` to decide (the queue must not be a way around the per-language translation permission). Queue = `communityStatus IN ('rejected','disputed') AND verified IS NOT 1`. Actions: keep (verified=1), replace (new value + verified=1), clear (value → NULL; the row is kept because deleting it would cascade the votes away). When counting this queue through Prisma use `OR: [{verified: null}, {verified: {not: 1}}]`, not `NOT: {verified: 1}` — SQL `NOT (verified = 1)` drops the NULL rows, i.e. the whole hsb/dsb import.
- **Capitalized translations (bulk-import artifact) — mostly fixed 2026-09-19**, `scripts/db/2026-09-19-normalize-translation-capitalization.ts` (dry run by default, backup `interlex.db.backup-before-capitalization`, one `audit_logs` row per change as `script:normalize-capitalization`, JSON change lists `translation-capitalization-report-*.json`, gitignored). 32 815 rows lowercased; pool share capitalized: hsb/dsb 72% → 14%, ru 100% → ~50%. Maintainer's rule: **a translation is capitalized only if `Lexeme.properNoun` is set** — but the flag is missing on ~13% of the capitalized nouns that remain (Уфа, Люблин, Кострома, Гамбург), so the script does not trust it for nouns. What it does instead, and why — read the script header before changing it: (1) evidence from the proofread languages (pl, cs, sk, hr, sl, uk, be — capitalized ≈ proper nouns there): all of a meaning's reference *languages* lowercase → artifact; a language counts as capitalized only if ALL its rows for the meaning are (a duplicate artifact row "Ale" next to "ale, lecz" used to block itself and everything else); (2) POS tier for meanings without references — never for nouns; (3) `--trust-proper-flag` for non-noun POS in ru/uk/be/bg (+ sr/mk minus adjectives) only. Skipped on purpose: `de` (nouns inside verb entries: "Form", "Wunde"), `eo`, `nl`, `cu`; English words that English itself capitalizes (Jewish, Christian, Russify — Dutch is not a safeguard, it writes religions lowercase); rows with German/English import junk in hsb/dsb (`ä ö ü ß`, or a variant equal to the de/en translation); rows with a capital left inside; rows whose FIRST variant is lowercase (a later capital is deliberate: "североморский, Северного моря"). Run until it reports 0 — fixing a reference-language artifact releases a second wave. **Still open**: 3 144 noun lexemes with `properNoun=0` and capitalized translations need a human pass over the flag (then the rest can be lowercased); signals that help order that review: all reference languages capitalized (14 lexemes), and mid-sentence capitalization in the ISV corpus (104 lexemes; false positives are homographs of names — kalina, sova, mraz, bog). Four hsb/dsb junk rows were slightly degraded by an early pass ("Wohnsitz nehmen", "(Lkw, Lkw)", "Niedergang") — restorable from `translation-capitalization-report-pass1.json`. SQLite's `lower()` does not handle Cyrillic — do case work in JS.

## Phase 3: public profile, leaderboard, completeness, moderator proposals (2026-09-23)

- `lib/community/publicStats.ts` (read-only interlex.db, tested): `fetchContributorSummary` (totals, accuracy, confirmed translations, streak via `computeStreak`, 12 weekly buckets, per-language rows — control cards never counted), `fetchLeaderboard` (flagged participants excluded), `fetchCompleteness` (per language: moderator / community / in progress / queued / unchecked), `fetchModeratorCandidates` (≥200 resolved, accuracy ≥0.9, ≥10 controls at ≥0.9, not flagged — thresholds are constants there).
- `/u/[handle]` (`lib/community/publicProfile.ts`, `robots: noindex`): exists only for users with a `UserProfile`; shows handle, bio, language flags and `ContributionStats`. `/contribute/leaderboard` (`?period=week|all&lang=`) names people only via `resolvePublicNames` → "Anonymous" without a handle. `/contribute` now also shows the visitor's own stats and `CompletenessBoard` (roadmap #76) to everyone, `/profile` shows the same stats block.
- Moderator proposals live on `/admin/platform/users` (`moderator-candidates.tsx`): the admin clicks "Выдать права" → `promoteToModerator` sets `MODERATOR` (if not already), grants `translate_<lang>` + `CommunityReview`, writes `RoleAudit`. No automatic promotion anywhere.
- **`/admin/proper-nouns`** (`Feature.WordsEdit`, `lib/community/properNounReview.ts`, tested): the human pass over `Lexeme.properNoun` that the capitalization script needs. Queue = `proper_noun_signals` (`ProperNounSignal` model; filled by `scripts/db/compute-proper-noun-signals.ts` — re-run after bulk translation edits, never during a corpus reanalysis) = lexemes without the flag that have a capitalized translation outside de/nl/cu/eo; 100 per page, suggested-as-proper first and pre-ticked (all reference languages capitalized, or ≥80% mid-sentence capitals in the ISV corpus; homographs of names — bog, jaj, sova — show up here and are unticked by hand). Save: ticked → `properNoun=1` (+ `Lexeme.updatedAt`), unticked → `lowercaseVariants` on every translation outside the skipped languages, written directly (votes stay valid — a case fix is not a new value), one `audit_logs` row per change, row removed from the queue. Case helpers moved to `lib/capitalization.ts`, shared with the script. 4 593 lexemes were queued when built.

## Phase 4: public change history on the word page (2026-09-23)

- `lib/community/wordHistory.ts` (tested): `audit_logs` for `(entityType='Lexeme', entityId)` grouped by `actionId` (one save = one entry, newest first, paginated by action), restricted to public fields — `value stem pos gender animacy declension conjugation properNoun isv nsl mergedFrom` and `<lang>.value / .communityStatus / .created`. `*.message`, `*.verified`, frequency, valency, inflection anomalies never leave the server; an action with only such fields is not listed at all. **`userEmail` is never selected into the DTO** — `classifyAuthor` turns it into `community` / `script` (`script:*`/`system:*` with no userId) / `moderator`, and `loadWordHistory.ts` attaches the handle via `resolvePublicNames` (two DBs, two phases). Without a handle a moderator is shown as "модератор".
- First page (10 actions) is server-rendered in `app/words/[id]/page.tsx` and passed to `Word.tsx` → `WordHistory.tsx`; further pages come from the public `GET /api/lexicon/[id]/history?offset=` (no session; the proxy's general /api limiter applies). Field/author/status labels live under `word.history` in the messages; the language name comes from `TRANSLATION_LANGUAGES`.

## Phase 5: discussion thread on the word page (2026-09-23)

- `word_comments` (interlex.db, `WordComment`, migration `scripts/db/2026-09-23-add-word-comments.ts`): one thread per lexeme, **one level of replies** (`createComment` refuses a reply to a reply), `status` `visible | hidden (moderator) | deleted (author)`. Hidden/deleted rows are never removed: replies hang off them and reports point at them; a hidden root shows as a placeholder only while it has visible replies, a hidden root without them is not listed. A hidden comment keeps its body in the DB for the moderator; a deleted one has it wiped.
- Writing needs a session **and a public handle** (`POST /api/words/[id]/comments` → 403 `handle_required`); reading is public. No `Feature` for participants; `Feature.CommentsModerate` only for hiding. Own edit/delete via `PATCH/DELETE /api/community/comments/[id]`, only while `visible`.
- Rate limits in `checkCommentAllowance`, counted from the table (survive restarts): 5 per 10 min; a user with no `contributor_stats.votesTotal > 0` gets 2 per hour.
- Post-moderation through the existing reports queue: `ReportErrorModal` accepts `entityType="Comment"` (reasons `abuse | other`, `entityId` = comment id, `reportedValue` = excerpt), `app/api/reports/route.ts` allows the type, `/admin/reports` shows a "Скрыть комментарий" button that hides the comment and resolves the report in one action (`hideCommentAction`, needs `ReportsReview` + `CommentsModerate`). There is no separate comments admin page — hiding is only ever a reaction to a report.
- `loadComments.ts` attaches handles via `resolvePublicNames` and computes `own` for the viewer; the public DTO carries no `userId`. `/contribute` lists the 8 latest comments.
- `lib/dedup/mergeLexemes.ts` now calls `rewireCommentsLexeme` — any other lexeme-merge script must do the same (grep for `inflection_anomalies` rewiring to find the spot).
