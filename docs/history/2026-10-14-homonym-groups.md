# Массовая разметка омонимов корпуса (roadmap п.111) — 2026-10-14

> Правило массового применения из этой записи заменено 2026-10-18: одинаковая форма и набор кандидатов не гарантируют одинаковую лексему в разных контекстах. См. [контекстную проверку и откат](2026-10-18-contextual-homonym-review.md).

Одно решение модератора закрывает все токены группы: токены с одной и той же
нормализованной словоформой и одним и тем же набором **конкурирующих лексем**
собираются в группу, а страница `/admin/corpus/homonyms` применяет выбор лексемы
ко всей группе сразу. До этого `TokenSidebar` решал ровно один токен за клик.

## Почему это вообще нужно: замер опроверг прежнюю оценку

В `app/admin/dashboard/page.tsx` стояла сноска: «из 786 419 токенов, где два
лучших кандидата почти равны, 779 616 (99,1%) спорят о граммеме ОДНОЙ И ТОЙ ЖЕ
лексемы… реально требуют человека лишь ~6 800 токенов». Прямой замер
`scripts/db/measure-corpus-ambiguity.ts` (он считает число РАЗНЫХ лексем среди
`CorpusTokenCandidate`, а не `matchCount`) на локальной копии `corpus.db`
(5,07 млн токенов) дал другое:

| Разных лексем у токена | Токенов |
|---|---|
| 1 | 2 440 384 (69,1%) |
| 2 | 823 457 |
| 3 | 240 324 |
| 4+ | 26 281 |

То есть с конкуренцией **разных** лексем — 1 090 062 токена (30,9%), а не 6 800.
Топ форм: `ne` — 79 818 токенов, `na` — 52 009, `se` — 41 908, `ja` — 38 823,
`je` — 34 184. Сноска в дашборде была обновлена.

Именно этот масштаб и делает группировку обязательной: 1,09 млн токенов — это
не «порешено кликами», но они схлопываются в считанные тысячи групп, потому что
токены одной формы делят один и тот же набор кандидатов.

## Что попадает в очередь, а что нет

В группу идут только токены, где конкурируют РАЗНЫЕ лексемы. Когда спор идёт
лишь о граммеме одной и той же лексемы (лексема и часть речи уже верны), размечать
нечего — это работа ранжирования и синтаксического разбора, и такие токены
(`homonymGroupKey IS NULL`) в очередь не выносятся. Это осознанное сужение: выбор
лексемы для группы корректен для всех её токенов, а выбор граммемы — нет, она у
каждого токена своя.

## Ключ группы — колонка, а не производная таблица

Рассматривались два подхода. `CorpusClusterSignal`/`CorpusNgram` в этом проекте —
производные таблицы, пересчитываемые целиком, и вариант «таблица групп +
пересчёт по расписанию» укладывался в эту конвенцию. Но пересчёт требует
полного GROUP BY по `CorpusTokenCandidate` (12,9 млн строк) — ~2,5 минуты на
живой базе, — и очередь устаревала бы между пересчётами.

Выбрано другое: `CorpusToken.homonymGroupKey` (nullable) заполняется **на путях
записи токенов**, где список кандидатов и так в памяти:

- `lib/corpus/reanalyzeDocument.ts::persistUpdates` — считает ключ из
  `TokenUpdate.candidates` для обоих путей переразметки (документного и
  пооткрытого по предложениям), поэтому они не разъезжаются;
- `lib/corpus/upsertDocument.ts` и `app/api/corpus/save/route.ts` — при первичной
  заливке документа.

Тяжёлый полный проход по кандидатам остался только разовым бэкфиллом на уже
размеченном корпусе. Для этого `TokenUpdate` получил ещё и `surfaceForm` (сама
словоформа в `data` не входит — та уходит в `updateMany` как есть).

Ключ: `"<normalizeSurfaceForm(форма)>\u241F<слаги лексем через |>"` (разделитель
␟ — как в `CorpusNgram.ngramKey`). Слаги сортируются, поэтому порядок кандидатов
на группу не влияет. Чистая функция `homonymGroupKey` вынесена в
`lib/corpus/homonymGroup.ts` без единого обращения к БД — иначе рантайм-путь и
скрипт бэкфилла рано или поздно разошлись бы.

Попутно `normalizeSurfaceForm` вынесена из
`lib/corpus/candidates/reconstruct.ts` в `lib/corpus/surfaceForm.ts` (модуль без
импорта `@/lib/prisma`): её тянет бэкфилл на better-sqlite3, и Prisma ему не
нужен. `reconstruct.ts` реэкспортирует функцию, существующие импорты не тронуты.

## Массовое применение — тремя SQL-апдейтами

`resolveTokenHomonymGroup(groupKey, wordSlug)` (`lib/corpus/resolveTokenHomonym.ts`)
не идёт циклом по токенам: в верхних группах по 50–80 тыс. токенов, построчный
Prisma-цикл занял бы минуты. Три `$executeRaw` в одной транзакции:

1. всем кандидатам, кроме выбранной лексемы, `rank = rank + 1` (освобождаем rank 0);
2. лучшему кандидату выбранной лексемы у каждого токена — `rank = 0, source = 'manual'`
   (скалярная подвыборка `ORDER BY rank, id LIMIT 1` даёт ровно один id на токен);
3. самому токену — `wordSlug/lemma/pos`, `matchCount = 1`,
   `resolutionSource = 'manual'`, `homonymGroupKey = NULL`, а `feats` берутся
   `COALESCE`-подзапросом из его собственного кандидата на выбранную лексему.

Параметров-идентификаторов нет вовсе: все подвыборки идут по индексированному
`homonymGroupKey`, а не по списку id (иначе на 80 тыс. значений повторился бы
`RangeError` из `reanalyzeDocument.ts`). Порядок шагов важен: шаги 1–2 выбирают
токены по ключу, и лишь шаг 3 его обнуляет.

Выбранная лексема обязана быть среди кандидатов группы: произвольный слаг из
запроса не принимается, иначе опечатка модератора разошлась бы по всем токенам.

## Проверка

- `lib/corpus/homonymGroup.test.ts` — 8 тестов на чистую функцию: порог в две
  разные лексемы, дедуп и пустые слаги, независимость от порядка, кириллица
  через ту же нормализацию, слаги с запятыми/дефисами, round-trip `parse`.
- `npm run typecheck:gate` — 116 ошибок, baseline 116 (новых нет).
- `npm run test:run` — 54 файла / 406 тестов зелёные.
- Локально применены DDL-миграция и бэкфилл на живой копии (5,4 ГБ):
  **1 090 062 токена схлопнулись в 8 743 группы** — то есть 1,09 млн кажущегося
  объёма это 8,7 тыс. решений модератора. Топ групп: `ne` (80 287 токенов,
  ne-ADV/ne-INTJ), `na` (53 010, na-ADP/ja-PRON), `se` (42 693,
  se-PRON/sej-PRON/sejati-VERB), `ja` (39 366, ja-PRON/on-PRON),
  `je` (35 136, byti-VERB/jesti-VERB/on-PRON).
- Сквозная проверка на живой базе: `countHomonymGroups` 8 742 группы за 205 мс,
  список из 20 групп — 162 мс; выбор лексемы на пробной группе из 2 токенов →
  `resolvedTokens: 2`, `resolutionSource='manual'`, ключ обнулён, повторный
  вызов — честный `not_found`.

Два бага поймала именно эта сквозная проверка (оба прошли tsc и тесты):

1. **`$queryRaw` не разворачивает JS-массив в `IN (...)`**: запрос с
   `WHERE "homonymGroupKey" IN (${keys})` падал с «SQLite3 can only bind
   numbers, strings…» — массив передавался как один параметр. Нужен
   `Prisma.join(keys)` из `@/prisma/generated/corpus/client`. Без этого страница
   не открывалась вовсе.
2. **Одиночного индекса по ключу не хватало**: `COUNT(*)` по нему был
   index-only, но `COUNT(DISTINCT documentSlug)` требовал чтения `documentSlug`
   из таблицы по случайным rowid — рендер списка занимал ~5,3 с. Составной
   индекс `(homonymGroupKey, documentSlug)` покрывает оба запроса (префикс —
   сам ключ) и заодно префиксный поиск по ключу; список стал 162 мс.

Подводный камень бэкфилла: better-sqlite3 запрещает открывать пишущую транзакцию,
пока на том же соединении жив читающий курсор (`.iterate()` + `db.transaction()`
в одном цикле → `TypeError: This database connection is busy executing a query`).
Запись идёт постранично `.all()`-батчами по `rowid` временной таблицы (курсор
закрыт до возврата). Первый прогон упал на этом до единой записи, ключи не
пострадали — скрипт идемпотентен.

## Открытое

- **На проде не применено**: DDL-миграция и бэкфилл идут через реестр
  (`bash prod.sh run ...`, бэкфилл с `--detach`). Пока бэкфилл не прогнан,
  очередь на проде будет пустой — новые токены ключ получают сразу, но уже
  размеченные 5 млн — нет.
- **Полный реанализ (п.30) проставит ключи сам** и заодно переразметит формы
  после правок распознавания 2026-09-15 — это и есть штатный путь обновления
  очереди после изменений движка.
- **Многие группы — это дубликаты лексем в словаре**, а не реальная омонимия:
  подсказка со ссылкой на `/admin/deduplication` есть в карточке группы, но
  автоматически отличить дубль от омонима нельзя (это лингвистический факт).
