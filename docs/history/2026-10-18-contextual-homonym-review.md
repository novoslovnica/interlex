# Контекстная проверка омонимов и откат пакетов — 2026-10-18

## Исправленная предпосылка

Одинаковая словоформа и одинаковый набор конкурирующих лексем НЕ означают,
что одна лексема правильна во всех предложениях. Группировка п.111 остаётся
навигацией по очереди; прежний `resolveTokenHomonymGroup` удалён. Запрос
старого клиента без списка вхождений теперь получает HTTP 400.

## Применение

Редактор открывает группу и читает до 50 контекстов за страницу. Точное
вхождение выделяется по последовательности токенов предложения (если
выравнивание не удалось, показывается предупреждение и позиция токена).
Все чекбоксы изначально сняты; следующая страница сбрасывает выбор.
Выбор лексемы действует только на отмеченные tokenId.

Сервер требует 1–50 уникальных положительных 64-битных id и SHA-256 ревизии
показанного состояния: токен, текст предложения, все кандидаты. В короткой
`BEGIN IMMEDIATE` транзакции проверяются ВСЕ выбранные вхождения: группа,
автоматический статус, ревизия и наличие выбранной лексемы. Если изменилось
хотя бы одно — HTTP 409, без частичного применения. Граммемы берутся из
лучшего кандидата выбранной лексемы отдельно для каждого токена; UI явно
указывает, что это автоматические признаки, а не проверка грамматики.

## Журнал и откат

В corpus.db добавлены `corpus_homonym_batches` (автор, время, группа,
лексема, кто и когда запрашивал откат) и `corpus_homonym_batch_entries`
(состояние до/после, tokenId, active/conflict/undone). История создаётся
атомарно с правкой. FK на токены намеренно нет: удаление документа не должно
стирать свидетельства модерации. Никаких записей в interlex.db/AuditLog.

SQL-триггеры переводят active-запись в conflict при любом последующем
UPDATE/DELETE токена или INSERT/UPDATE/DELETE его кандидата. Это защищает и
точечное ручное решение, записавшее те же значения: одного сравнения значений
было бы недостаточно. Перед откатом также сверяется полное after-состояние,
включая текст предложения. Восстанавливаются только неизменённые вхождения:
лексема, граммемы, статус, ключ очереди, исходные rank/source кандидатов.
Конфликты пропускаются с отчётом; повторный откат ничего не меняет.

Доступ к применению, истории и откату требует
`Feature.CorpusTokenDisambiguate`. История пакетов с пагинацией доступна на странице
`/admin/corpus/homonyms`; история хранится в БД, а не в сессии браузера.

## Замена corpus.db

`corpus-export-manual.ts` выгружает журнал вместе с ручными решениями.
`counts.homonymHistory` — checksum всего журнала, поэтому проверка после
остановки службы замечает и новый пакет, и откат, и конфликт, даже если число
ручных токенов не изменилось. Экспорт самодостаточен для копирования на сервер.

Импорт сохраняет журнал, но active-записи помечает conflict: before/after
снимки привязаны к исходным id токенов и кандидатов; применять их к
перетокенизированной базе опасно. Сами актуальные ручные решения переносятся
по прежним стабильным ключам. Откат нужных пакетов следует выполнить ДО
замены корпуса; после неё история остаётся свидетельством для ручной проверки.
Правки, сделанные старым механизмом без журнала, достоверного before-снимка
не имеют: автоматически восстанавливать выдуманное состояние нельзя.

## Выкладка

Миграция `scripts/db/2026-10-18-add-homonym-review-history.ts` зарегистрирована
как schema и выполняется штатным релизом при остановленной службе. Она
идемпотентно создаёт таблицы, индекс и триггеры; не сканирует корпус и не
переписывает токены. На разработческой копии её тоже нужно применить через
реестр перед открытием обновлённой админки. Production в этой задаче не менялся.

## Проверки

Интеграционные тесты на SQLite `:memory:` проверяют ограничение выбранными
контекстами, устаревшие ревизии, атомарность, восстановление rank/source и
ключа очереди, повторный откат, конфликты после точечных/raw SQL правок,
удаление токенов и кандидатов, пагинацию и перенос журнала при пересборке.
Тесты API проверяют запрет старого group-wide запроса, отсутствие сессии,
feature permission и HTTP 409.
