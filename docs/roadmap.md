## P1 — риски безопасности и целостности данных

4. ✅ **Nonce/replay-защита для Telegram-логина** (2026-08-12) — HMAC-хэш от Telegram уникален на каждое событие логина, поэтому сам служит nonce'ом: новая таблица `telegram_auth_nonces` (auth.db, миграция `scripts/db/2026-08-12-add-telegram-auth-nonce.ts`), claim через `INSERT OR IGNORE` (атомарно на уровне SQLite, устойчиво к параллельным запросам с одним payload'ом) в `lib/telegramAuthNonce.ts::claimTelegramAuthHash`, подключено в `auth.config.ts`'s `authorize()` между проверкой freshness (24ч) и возвратом пользователя. Попутная уборка строк вне 24ч окна — раз на каждый логин, отдельная DB-нагрузка незначительна при объёме проекта. Покрыто тестом с замоканным `@/lib/prisma` (без обращения к живой БД). Бэкап `auth.db.backup-before-telegram-nonce` перед применением DDL.
5. ⬜ **Разрешить Prisma migration drift на `interlex.db`** (`prisma migrate diff` + ручная baseline-миграция) — сейчас `migrate dev` предлагает full reset живой БД.
6. ✅ **`ų`/`u` кандидаты в `DbAnalyzer`** (2026-08-12) — лингвистический вердикт от мейнтейнера: обычная буква (`u`) — расширенное множество, покрывающее и себя, и упрощённое написание канонической (`ų`), но не наоборот; принцип общий для всех подобных пар букв ISV-орфографии, не только u/ų. Реализовано как отдельный `lib/corpus/tokenizer/spellingVariants.ts` (`expandSpellingVariants` — декартово произведение по расширяемым позициям слова, таблица `SIMPLIFIED_TO_CANONICAL` пока содержит только подтверждённую пару `u→['ų']`, расширять только по факту лингвистического подтверждения, не гадая). Подключено в `DbAnalyzer.analyzeWord`: варианты написания расширяются один раз в начале, дальше участвуют в поиске `inflection_anomalies`, генерации гипотетических баз (`generateHypotheticalBases`) и стем-префиксном фоллбеке (`findBestStemPrefixWord`) — везде объединяются в общий пул кандидатов, а не замещают точный поиск (тот же урок "не терять кандидата", что и в истории с `sųt`/`byti-VERB` vs `sut-AUX`, см. AGENTS.md). Продакшен-запрос (`createQueryWordsByBase` в `analyzer-factory.ts`) не потребовал изменений — просто получает более широкий список `bases`. Покрыто тестами (`spellingVariants.test.ts`, `dbAnalyzer.test.ts` с замоканным `queryWordsByBase`, без обращения к живой БД). Открыто: перепрогнать `scripts/db/2026-07-28-reanalyze-all-documents.ts` на реальном корпусе, чтобы фактически переразметить "sut"-вхождения (2325+) — не сделано в рамках этой сессии, отдельное решение (трогает продовые данные).
7. ✅ **Rate limiting на публичных API** (2026-08-12) — `lib/rateLimit.ts` (`RateLimiter`, in-memory fixed-window по IP — корректно для текущего деплоя, один долгоживущий `next start` процесс, без Redis; понадобится общее хранилище только если проект когда-нибудь станет многоинстансовым) + `getClientKey` (`x-forwarded-for`/`x-real-ip`, иначе общий bucket `"unknown"`). Подключено в `proxy.ts`: лимит 120 запросов/60с на клиента для всего `/api/**`, кроме `/api/auth/**` (не троттлится и не гейтится — часто дёргается при обычной загрузке страниц). Проверено вживую в браузере: 130 запросов подряд к `/api/lexicon` → 119 успешных + 11 с `429` и корректным `Retry-After`; `/api/admin/*` и обычный `/api/lexicon` не задеты регрессией. Покрыто юнит-тестами (`rateLimit.test.ts`, чистая логика без `NextRequest`).
